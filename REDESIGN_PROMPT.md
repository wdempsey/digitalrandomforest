### 1. The invariant — what must survive untouched

The site's information architecture is modeled on Maggie Appleton's digital garden and
**that structure is not up for redesign.** Specifically, preserve:

- **Garden IA**: Garden → Essays / Notes / Patterns / Library, with Topics as an
  orthogonal overlay driven by frontmatter. No new taxonomy, no faceted filtering UI.
- **Growth/status metadata as a first-class citizen** — `Published`, `Updated`, `Status`,
  `Version` via `ScholarlyMeta`. Visible, subtle, never dominant.
- **Reading-first single-column essay body** with a comfortable measure, plus the
  asymmetric rails: `TableOfContents` left, `Backlinks` right, on essay pages only
  (see `isEssayReadingPage` in `quartz.layout.ts`).
- **Tufte-style sidenotes and the figure/sidenote gutter** (`--sidenote-gutter`,
  `Plugin.Sidenotes()`, `Plugin.Figures()`).
- **Wander affordances staying subordinate**: `ReadNext`, `TopicConnections`, backlinks,
  graph — present, quiet, never the main event.
- **The editorial, hand-curated homepage.** Never an autogenerated dashboard.
- **`EssaySketch`** — the one quiet illustration slot per essay.
- Light **and** dark mode, both first-class.

If a print-tech idea requires deleting or demoting any of the above, the idea loses.

---

### 2. The change — "print-tech"

Print-tech = **editorial print DNA crossed with technical instrumentation.** The page
should read like a well-set journal or field manual that happens to be produced by
someone who works in code and statistics. Concretely:

**Type**

- Serif display carries the hierarchy; keep it literary and commit harder to size contrast
  between H1 / H2 / body than the current scale does.
- **Promote `IBM Plex Mono` from a code-only font to a labeling system.** Mono is the
  "tech" half: eyebrow kickers, section numbers, `Status`/`Version` values, figure and
  table captions, topic chips, nav state, RSS/date stamps. Small, tracked-out, uppercase
  or small-caps where appropriate.
- Tabular figures for anything numeric. Real small caps if the family supports them.

**Structure**

- Rule-work: hairline rules, visible margins, spec-sheet-style key/value rows for
  metadata. Borrow the page furniture of print — folios, running heads, section numbering
  (`01 · 04`), registration-mark details — used sparingly.
- Grid and alignment should be _legible_. The reader should be able to feel the column.
- Diagram/blueprint texture is welcome where it's already earned: figures, the graph view,
  `EssaySketch`. Not as background decoration.

**Discipline — do not**

- gradients, glassmorphism, glow, blur, animated blobs, floating card shadows on
  everything, hero video, or any SaaS-landing-page vocabulary
- decorative motion; any motion must be sub-200ms and respect `prefers-reduced-motion`
- emoji as iconography
- anything that makes this read as developer documentation or a dashboard

### 3. Palette — propose before you implement (HARD GATE)

References to study and synthesize:

- **https://pi.dev/** — near-neutral, mono-forward, technical minimalism, unusually strong
  light/dark parity, restraint as the whole point.
- **https://www.chaseai.io/#services** — deeper contrast, more committed accent, more
  confident sectioning and numbered steps.

The current palette is warm parchment (`--paper-bg: #faf8f4`, sage `--accent: #6f8c7a`).

**Produce three named palette directions as an Impeccable direction plate** — a system
board showing background, surface, text primary/secondary, borders, accent, and code
surface, in **both light and dark**, plus one first-surface mock of an essay page.

Constraints on every candidate:

- Light and dark are peers, not a theme and an afterthought. Contrast and hierarchy parity.
- Body text ≥ WCAG AA; ideally AAA at the reading size.
- Retain enough warm bias that the site does not read as a cold dev-docs template. Cool
  neutrals are allowed, sterile ones are not.
- One accent, used structurally (links, active state, rules) — not sprinkled.
- Must survive KaTeX block math and `github-light`/`github-dark` syntax highlighting
  sitting inside it without visual dissonance. Check this explicitly; the site carries a
  lot of equations and code.

**Stop and present the three directions. Do not write a line of CSS until one is chosen.**

### 4. Implementation order (after the palette is approved)

1. **`quartz/styles/custom.scss` `:root` token block + `quartz.config.ts` `theme.colors`.**
   These two must stay in sync — Quartz's `--light`/`--dark`/`--secondary` vars and your
   `--paper-*`/`--text-*` vars currently overlap. Reconcile them; don't leave two sources
   of truth. Do the same for `theme.typography` if the type stack changes.
2. **Type scale** — the `--type-*` custom properties. Widen hierarchy contrast; define the
   mono labeling scale as explicit tokens (`--type-label`, tracking, weight).
3. **Base typography + page layout** sections of `custom.scss` (lines ~73–384).
4. **Navigation and side panels** (~384–584) — `TopNav`, TOC rail, backlinks rail.
5. **Metadata & chips** — `ScholarlyMeta`, `TagList`, `PageList` cards (~819–945). This is
   where print-tech pays off most: make status/version read like a spec sheet.
6. **Figures, sidenotes, callouts** (~584–819). Captions go mono. Keep the gutter behavior.
7. **Homepage** (~945–1117) and `HomeCover.tsx`.
8. **Responsive** (~1117–end) and dark-mode parity sweep.
9. **`syntax.scss` / `callouts.scss`** last, so code and callouts resolve _into_ the new
   palette rather than sitting on top of it.

Component `.tsx` edits are in scope where markup blocks the design (adding a class, a
mono label wrapper, a section number). **Do not change component logic, props, or the
data each component reads.**
